Chapter 6The data model and the database

Everything the pipeline knows lives in one SQLite file, jobs.db. This chapter covers the Python models, the tables, and the five rules that keep the database in step with the job feeds.

Pydantic models (pipeline/models.py)

A Pydantic model is a class whose fields have types. Creating one validates the data: a missing required field or a wrong type raises an error instead of silently storing garbage. Connectors produce Job objects; the fetcher wraps each board's outcome in a FetchResult.

{{py pipeline/models.py Job}}

Two computed fields are derived, never stored by hand:

  • id joins source, board and the ATS's own job id: greenhouse:doximity:8132424. It is stable across runs, so the same job is recognised every day.
  • content_hash is the first 16 hex characters of a SHA-256 over title, location and description. If the employer edits the posting, the hash changes and the job goes back to the AI; if not, its stored extraction is reused.
What is a hash?

A hash function turns any text into a short fixed-length fingerprint. The same input always gives the same fingerprint, and a tiny change gives a completely different one. That makes it a cheap way to ask "did this posting change?" without comparing whole descriptions. The \x1f separator (an invisible "unit separator" character) keeps "ab" + "c" from hashing like "a" + "bc".

The five diff rules

Each day the pipeline gets a fresh list of open jobs per board and must update the database. apply_result is the heart of it, and implements five rules written down in docs/SPEC.md:

  1. Seen again: refresh last_seen_at and clear expired_at (a job can come back).
  2. Missing from a successful fetch: the job is gone, set expired_at. Rolling feeds (Jobicy) are the exception: they expire by age.
  3. A failed fetch never expires anything. If Greenhouse is down for an hour, its jobs must not vanish from the site.
  4. Content changed: send the job back to the AI (classify_status = 'pending').
  5. Five failures in a row: retire the board.
{{py pipeline/db.py apply_result}}
Reading the code
  • with conn: opens a transaction: either every change for this board is saved, or none is (if an error happens halfway).
  • existing maps each known job id to its hash, expiry and "since" date, loaded in one query instead of one per job.
  • seen guards against feeds that list the same job twice.
  • The CASE WHEN ? THEN 'pending' ELSE classify_status END trick resets the status only when the content changed, in the same UPDATE.

Retiring boards removed from the list

{{py pipeline/db.py sync_boards}}

A board removed from boards.csv on purpose is different from a board that fails: its jobs are expired immediately. ON CONFLICT ... DO UPDATE is an upsert: insert a new board, or update the name and website of an existing one while keeping its health history.

Where the database lives

jobs.db is never committed to git (it is about 170 MB and holds full job descriptions). The daily workflow downloads it from the data-latest GitHub Release, works on it, and uploads it back, encrypted with AES-256. Chapter 18 shows how.
