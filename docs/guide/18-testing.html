Chapter 19Testing, linting and evaluation

The project's rule is "tests for anything that parses or decides, and no network in tests". 75 tests run in under two seconds. Separately, a hand-checked sample measures how often verdicts are right.

Running the tests

Fixtures: real feeds, saved once

tests/fixtures/ holds a real response from each job source (Greenhouse for Doximity, Lever for Spotify, Ashby for Supabase…). Tests feed them to the connectors' parse(), so they test real formats without touching the network.

{{file tests/conftest.py}}

A pytest fixture is a function whose return value is passed to any test that names it as a parameter. autouse=True applies no_sleep to every test: retry waits become instant, so tests about retries do not take seconds.

Testing the rules

Each of the five diff rules has its own test, against an in-memory SQLite database (":memory:", created fresh for every test):

{{py tests/test_db.py test_rule3_failed_fetch_expires_nothing}} {{py tests/test_db.py test_idempotent_second_run}}

The verdict tests cover each branch of decide() with small hand-made extractions, including the traps found in real postings (company slogans, regions in the title, time zone edges). The free-tier tests use monkeypatch to replace the AI calls with fakes that run out of quota at a chosen moment, and check that the next provider takes over and the rest is left for later.

Measuring accuracy (pipeline/classify/evalset.py)

Tests prove the code does what it says; they do not prove the verdicts are right. For that, evalset sample draws a stratified sample of 200 classified jobs (some of each verdict) into data/eval/eval.csv with an empty label column. A person reads each original posting and writes the true verdict. Predictions go to a separate file, so labelling stays blind. evalset score then reports the precision of "eligible" and "not eligible".
